# 相談の受付と保存結果

モバイルの相談は、認証済み所有者ごとの論理送信IDで受付・照会・中止を行う。通信の再送を新しい相談として実行せず、最新の会話を別の送信の結果と取り違えないための契約である。旧同期相談APIは互換用に残す。

## HTTP契約

`/consultation-requests/{request_id}`のPOSTは`consultation_id`（新規は0）、`message`、任意の`planned_amount`を受け取り202を返す。送信IDは16〜100文字のASCII英数字、`_`、`-`。受付前に入力長・金額・既存相談の所有権・利用上限設定の読取を検証する。JSONのSHA-256を保存し、同じID・同じ正規化内容は既存受付を返す。異なる内容は409。所有者ごとに処理中は1件で、別IDの同時受付は409。400・相談の404は未受付が確定した入力エラーで、モバイルは初回POSTとGET404後の同ID再受付のどちらでも入力を編集可能に戻す。結果不明や409では送信IDと内容を保持する。停止開始後の受付・照会・取消しは503 `service_stopping`で拒否する。未確定のIDと入力は保持し、再起動後に同じIDで結果を確認する。

GETは同じIDの結果を返す。他の所有者のIDは404。DELETEは中止を要求する。未受付のIDにもcancelledの記録を作り、そのIDを今後受付しない。受付直後にPOSTの通信が途切れた場合も、GET404から同じID・内容で受付を再試行できる。中止意図を保存したクライアントは404からPOSTへ戻らない。

応答は`request_id/status/expires_at/cancel_requested/error_code/result`。statusはprocessing/completed/cancelled/failed。completedは当該送信で保存した相談結果を必ず含む。処理中の中止は、金融変更なしのunavailable応答と入力を保存しcancelledにする。未受付の取消記録と保存失敗failedはresultがnull。結果はその後の会話が増えても当該送信時点のsnapshotを返す。

## 時間予算と取消し

新規受付のcommit成功時は、その確定metadataを返してworkerを起動する。commit後の同じHTTP contextによる再読取を起動条件にせず、切断直後もacceptedの処理を実行する。既存受付の再送だけはreceiptを読んで内容を比較する。

POST開始から結果保存まで絶対期限28秒。受付準備もこの中に含め、最後の5秒を保存用に確保する。モデルの全試行（最初1回と修正最大2回）は既存22秒と残余の小さい方に制限する。準備が遅ければモデル時間を短縮する。期限・中止後は回答を採用せず、金融計算をしない保存用fallbackに切り替える。モデルがcontextを無視して遅く戻っても、期限とreceiptの状態をSQL保存時に照合して二重保存・金融変更を拒否する。会話と利用者状態のversion検証も維持する。

受付後の実行はHTTP切断に依存しない。DELETEの中止フラグを100ms間隔で監視し、モデルcontextを中止する。保存txは受付行を先にロックする。中止が先なら正常回答を保存できず、保存が先ならDELETEはcompletedの保存済結果を返す。正常処理とfallbackが並走しても最初の1保存だけを許可する。

期限後の失敗状態整理・保存済結果の再読取・管理者通知は各最大5秒の独立した保守処理で、28秒の結果生成期限を延長しない。受付準備を開始した時点から寿命管理に登録し、終了待ちを開始するとmutexで新規受付・照会・取消しを閉じる。停止判定とWaitGroupへの登録を同じロックで直列化し、準備中の処理が終了待ち後にworkerを追加できないようにする。HTTP Shutdownが時間切れでも登録済みの準備・内部処理を待ってからRepositoryを閉じる。

プロセス終了では外側のworkerだけでなく、内部のモデル呼出し・chat.Send・監視も中止して終了を待ち、それらがRepositoryへアクセスし終わる前にDBを閉じない。contextを無視して終了しないモデルはGoから強制終了できず、結果の28秒期限は維持する一方でプロセスの安全な終了待ちには上限を保証できない。実プロバイダーのcontext対応は別途確認する。プロセス断で残ったprocessingは照会または次の受付時に期限超過failedにする。同IDを自動実行し直さない。failedではモバイルに保持した入力から利用者が明示的に新IDで再送する。

## 原子的保存と境界

受付と新規相談の月次1件予約は同じtx。相談、会話、利用者状態、購入期限索引、結果receiptを同じtxで確定する。保存済なのに結果照会だけ失敗しても月次予約を解放しない。failedの確定と未保存予約の解放も同じtxとし、二度解放しない。追加発言は新規件数を増やさない。月次上限の既存動作は維持する。

request_id/hash/受付metadataをLLMへ渡さない。結果snapshotは所有者の照会用で、外部モデルの検索対象に追加しない。金融解釈と計算は既存LLMの責務であり、fallbackはそれらを行わない。

## モバイルの待機と復帰

個々のHTTPは既存受信10秒。全体は45秒かつ最大24回の照会で打ち切り、最初2回は1秒、その後2秒間隔で待機する。28秒付近の保存結果を受け取れる余裕を持つ。処理中・照会中・中止中を表示し、入力や会話選択を固定する。期限内に結果を確認できなければ入力とIDを保持し「結果を確認」を表示する。

送信前に入力・ID・中止意図を安全なストレージへ保存する。接続先と既存認証セッションで分離し、別セッションへ復元しない。古いセッションの保存・削除は直列化し、遅い応答はgenerationとtoken一致を確認して破棄する。画面再作成時も未確定入力を復元し、結果確認は入力欄の空判定とは独立する。保存成功または確定failedで未確定記録を解除する。failedでも画面の入力は残して明示再送を可能にする。初回送信・結果確認・中止で保存済結果を取得できた場合は、未確定から保存成功への状態遷移で入力欄を一度だけ消し、履歴再取得待ちの間に入力された次の新しい相談文は保持する。元の入力を新IDで誤送信しない。中止のunavailable結果も入力をサーバーに保存済みなので同じ扱いとする。

## 検証

正規入口は`python3 tools/harness.py check server`、`check mobile`、`check docs`、専用DB設定で`check postgres`。制御モデルで切断・同ID再送・異内容拒否・所有者・最大2修正・context無視・取消し・保存後照会失敗・準備遅延を確認する。DBではreceiptと保存・件数の原子性、保存後取消し、期限・複数writerのfenceを確認する。mobileは取消404、画面復帰、入力エラー、遅い結果の破棄を確認する。実モデル・実機確認はこれらとは別に記録する。


## 2026-10-12の実モデルHTTP確認

独立レビューの6指摘を修正した完成候補を隔離コピーし、既存設定の`gpt-5-mini` / `medium`、専用PostgreSQL、合成ユーザーで認証付きHTTPを確認した。個々のHTTP受信期限は10秒のまま、受付は8ms、保存済結果の取得は約11.1秒だった。

同ID・同内容の再POST（202）が同じreceiptを返し、異内容は409になった。20,000円の購入予定を保存し、receiptの結果と相談GETのJSONが一致した。月次相談件数は再送後も1件。未認証とログアウト後は401だった。これは新APIの代表1ケースで、全入力の品質・遅延や実機の操作品質を保証しない。

最初の補助検証は再送ステータスを200と誤って期待してFAILした。契約どおり202へ期待を修正し、最終ソースで上記を再実行してPASSした。本体の不具合と区別する。実機・シミュレータ画面操作はMacのロック解除待ちで未実行。署名・インストールなしの隔離コピーではiOSシミュレータ用ビルドが成功した。
