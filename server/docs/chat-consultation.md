# チャット主体の支出相談

関連: [Issue #110](https://github.com/shuichiro-hayafuji/arran/issues/110)、[確定した相談要件 #16](https://github.com/shuichiro-hayafuji/arran/issues/16)、[責務分担 #20](https://github.com/shuichiro-hayafuji/arran/issues/20)。

## 責務と保存

新しい相談APIは`internal/consultation`のServiceとAgent・Repository Portを使う。OpenAI Adapterは金額抽出、計算、解釈、目標や嗜好を含む助言を構造化出力で返す。プログラムは金融判断を計算し直さず、出力形式・状態・整数円・厳しさの範囲を検証して保存する。旧Agentの固定verdictと金融fallbackは新しい相談APIへ接続しない。旧結果記録・取引集計・月次レビューは別経路として残る。

会話履歴は`chat_threads`、利用者ごとの記憶・厳しさ・CSV案内済み状態は`chat_states`に保存する。相談の既存一覧用情報も同じDBトランザクションで更新する。PostgreSQLは009の新規migration（既存の002〜008を保持）、SQLiteはテスト用の003スキーマを追加する。

記憶は意味を表すキー、値、本人の事実かLLMの推測か、対象期間、元の相談・発言への参照、記録時点を持つ。同じキーの訂正では旧情報を非アクティブにし、履歴として残す。時刻や信頼度による一律の除外はしない。厳しさは未指定5、指定1〜10を保存する。モデルへ渡すのは関連する最新のアクティブな記憶と同じ相談の直近8メッセージ（回答の根拠・前提を含む）で、別相談の会話全文は渡さない。別相談の直近20件を検索候補とし、現在の相談文と文字列が関連する発言・助言・根拠・前提を最大6件・JSON合計6000バイトまで渡す。出典の相談IDと記録時刻を保持し、過去の助言を本人の事実と混同しないようLLMへ指示する。削除以前の情報はこの検索にも含めない。

「忘れて」に対応した削除記録がある場合、旧会話からの復活を避けるため、以後のモデル入力から削除時点以前の会話全文・回答の根拠・前提を除く。削除後に新しく交わした会話は次の文脈に使用できる。画面で見える履歴は保持する。関連する派生推測の削除はLLMへ指示する。この保守的な方式では、削除後の応答に過去の細かな話題が反映されにくくなる。

初回の新しい相談では、旧プロフィールの非ゼロの金額・目標・カテゴリ設定と、旧メモリを一度だけ引き継ぐ。金額は旧情報の記録時点と出典を持つが、対象期間は不明のままにする。旧スキーマでは欠損と明示的な0円を区別できないため、ゼロの金額は引き継がず不足情報として扱う。旧メモリは確定した本人の事実と断定せず推測として渡す。削除後に旧データを再取り込みしない。旧プロフィールの厳しさは数値尺度が異なるため5で始める。新しい状態の作成後は会話の訂正を正とし、旧フォームの更新を同期しない。

関連情報は現在のメッセージと直近の利用者の発言の文字列を使って検索する。金融相談には残高・予算・収入・固定費・目標などの記憶を候補に加え、そのほかはキー・値と発言の文字列の一致で順位を付ける。外部送信は最大12件・記憶のJSON合計6000バイトとし、訂正で無効になった記憶は含めない。順位は検索だけに利用し、金額計算や助言の判定には使わない。意味の同じ言い換えを文字列で拾えない場合があるため、実モデル評価では必要な情報が欠けないことも確認する。

購入予定を抽出したときは、LLMが構造化した商品名・予定額・記録時刻を`pending_purchase`へ保存し、`purchase_confirmation_pending`とする。応答のstatusとは別に保持する。モデルの`purchase_change`がnullなら予定を保持する。setで金額だけ補足・訂正されたら、忘却後も外部入力に利用可能な既存の商品に限って保持し、同じ金額でも商品変更なら更新する。cancelで明示的に取り消されたら確認待ちを解除する。現在の確認待ち情報も外部入力に含め、商品名は除去処理を通す。削除時点以前の確認待ちは外部へ再送しない。外部入力に利用可能な予定がなければ、新しいsetは商品名を必須とする。商品名のない金額変更は不正出力として再試行し、旧商品の時刻を更新して復活させない。支出や残高には反映しない。購入確認・実績反映のライフサイクルは#22で扱う。

## CSV確定後の相談入力

Repository Portは同じ利用者の確定済み取引を直近100件まで読み、支出だけを日付・整数円・カテゴリのDTOへ明示転記する。CSVプレビュー段階ではまだ入力に入らず、確定後の次の相談で反映される。加盟店・明細本文・口座・CSV原文・fingerprint・他利用者の情報を外部DTOに含めない。テスト用SQLiteでは取込と同じトランザクションでchat専用の所有者表へ記録し、所有者不明の旧取引を外部候補にしない。入金は含めず、金額の符号変換や合計の金融計算をプログラムに追加しない。

取引入力には取得候補の上限と支出明細の開始日・終了日、常に部分データであることを付ける。全支出が記録されていると断定せず、未取込・候補外の支出を0円と扱わないようモデルへ指示する。忘却がある場合は、その時点以前のImportedAtを持つ取引をローカルで候補から除く。ImportedAt自体は外部へ出さない。この保守的な対策により、削除対象と無関係な既存CSVも外部へ渡りにくくなる。削除後に取り込んだ新しい明細は利用できる。

## APIと画面

- `POST /consultations`はmessageだけで相談を始められる。プロフィールとCSVを必須にしない。旧クライアントのplanned_amountは会話への補足として扱う。
- `POST /consultations/{id}/messages`は補足・訂正・再試行に使い、同じ相談IDと全履歴を保つ。
- `GET /consultations`と`GET /consultations/{id}`は保存済みのmessagesを返す。旧相談には新しい履歴がなく、旧相談をこの経路で継続する移行は未実装。
- 新しいstatusはanswered、provisional、needs_information、unavailable。固定の金融判定値ではなく応答の状態を表す。
- 同時送信は利用者の記憶と相談のversionを照合し、古い回答の上書きを409で拒否する。クライアントは入力を保持し、履歴を読み直して再送できる。

ログイン後は相談画面へ直接進む。専用の金額欄、プロフィール編集画面、メモリ管理画面への導線を外し、会話で補足や訂正を送る。CSVは最初のansweredまたはprovisional回答後にだけ任意機能として一度案内し、案内済み状態を再起動後も保持する。

## 失敗時と外部送信

モデル呼出しは初回込み最大3回、全体22秒で打ち切る。利用可能な別LLMは今回設定していない。すべて失敗したときは金融判断を返さず、unavailableと利用者の相談文を保存する。リクエストの期限切れ後も保存だけを最大5秒試みる。保存自体が失敗したときは成功応答を返さず、画面の入力を保持する。開発用mock設定でも金融判断を生成せず、unavailableになる。既存の日本時間による月次件数予約、利用者別上限、上限通知、usage保存を維持する。新規相談は上限回数まで外部LLMを使い、上限を超えた新規相談と上限到達後の追加メッセージは外部呼出しを止める。上限時は保存と利用不可の説明を返し、旧金融fallbackでは代用しない。追加メッセージは新規相談数へ数えない。

外部へ送る項目は現在時刻、厳しさ、除去済みの商品名を持つ現在の購入確認待ち、許可された取引DTOと取得範囲、メッセージ、直近の会話（本文・根拠・前提・時刻）、検索した記憶（キー・値・種類・期間・出典・記録時刻・有効状態）、検索した過去相談の発言・助言（相談ID・本文・根拠・前提・時刻）に限定する。本文・根拠・前提、記憶のキー・値・期間・出典は除去処理を通す。期間は妥当なISOの日・月・時刻のみ保持する。外部送信前に、ラベル付き認証情報と長い数字列を除去し、円が付いた金額は保持する。認証情報・口座番号・カード番号を要求・復元・保存候補にしないようモデルへ指示する。`store:false`を維持する。ただし自由文の無ラベルの秘密や、番号と金額のあらゆる表記を完全に識別する保証はない。正規表現とプロンプトだけで完全匿名化済みとは扱わない。

## 検証の区別

自動テストでは制御したモデル応答を使い、情報不足を0円にしないこと、概算と対象期間、訂正履歴、再起動後の復元、厳しさ、CSVの一回限り案内、忘れた情報の文脈除外、モデル失敗と再試行、競合拒否を確認する。PostgreSQLの所有者・トランザクション検証は専用DBで行い、SQLiteだけで本番DBの保証としない。

実モデルの抽出・計算・質問判断の品質、自由文の外部送信境界、利用者による利用、実機表示は別途確認が必要。制御したモデル応答での成功を、実モデルの正確性の証明とは扱わない。購入実績と残高反映は#22、CSVとの同一支出照合は#111で扱う。

構造化出力の仕様参照: [OpenAI公式ドキュメント](https://developers.openai.com/api/docs/guides/structured-outputs)。

## 実モデル評価の再開手順（未実施）

APIキーを安全な実行環境からプロセス環境へ設定し、`USE_MOCK_LLM=false`で専用DBのサーバーを起動する。秘密を入力・ログ・テストデータに含めない。認証した専用ユーザーで同じ相談へ順にPOSTし、GETの保存結果と照合する。

1. 「2万円のイヤホンを買いたい。残高は約5万円」と送り、不足を0円とせず必要な情報だけ質問すること、予定額が購入確認待ちで保存されることを確認する。
2. 質問に答えず別の話を続け、暫定回答の前提・不確かさか助言不能の理由、元の相談履歴の保持を確認する。
3. 「今月の自由予算は3万円。訂正、残高は約6万円。厳しさ8で」と送り、保存値の対象期間・概算・出典・事実と推測、訂正履歴を照合する。
4. 新しい相談とサーバー再起動後に同じ情報を言い直さず相談し、保存情報の検索、厳しさ、CSV案内の一回限り、過去の根拠と前提の履歴を確認する。
5. 目標の訂正・忘却を依頼し、次のモデル入力候補から削除情報と削除以前の履歴が除かれ、無関係な記憶が送られないことを専用データで確認する。

これらは制御した応答の自動テストとは別の品質確認である。モデルの抽出・計算・質問判断が代表ケースを満たすまで、実モデル品質の完了判定を行わない。
