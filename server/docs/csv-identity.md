# CSV明細の同一性とキー移行

同日・同額の支出が複数ある場合や、同条件の入金がある場合も、それぞれ保存する。加盟店の分類に使うNormalizeMerchantと、明細が同じかどうかの判定を分ける。カテゴリ訂正をキーに含めず、再取込で元の訂正を上書きしない。

## 識別の根拠

所有者・取込元・口座で明細を分離する。取込元は銀行やカードサービスを、口座名はその中の口座を識別する利用者の指定であり、同じ口座の再取込では同じ値を使う。モバイルの旧値は`manual_csv`・`個人`。既存の履歴を再取込する場合はその指定を維持する。別の名前が同じ実口座だとは推定しない。表示上の「手動CSV」は`manual_csv`へ対応する。

安定した明細IDがCSVの実在列にあるときだけ、列の割当でその列を明示指定する。汎用の番号や参照番号を自動で銀行取引IDとみなさない。取込元と口座の指定を必須とし、空ID・存在しない列・同一IDの異なる内容を拒否する。IDは所有者・取込元・口座・収支種別の範囲で識別する。異なる銀行・口座や支出と入金に同じID文字列があっても統合しない。同じ安定IDの内容が既存記録と変わっている場合は上書きせず取込を拒否する。訂正・取消しはこの機能で実行しない。

同じCSV内で同じscopeの安定IDが繰り返される場合は、内容が同じでも入力全体を拒否する。複数物理行を同じ明細へ自動集約すると行対応が失われ、後の列変更で二重計上になるためである。previewは400入力エラーとして取引ID列と重複行の確認を案内する。adapter直呼出しでも全batchを拒否し、明細・alias・行対応を部分保存しない。行の自動削除やID列の自動解除は行わない。異なるCSV間で同じ安定IDを再利用する通常の重複除外、IDなしの正当な同条件複数行、各行の異なるID、異owner・口座・収支の分離は維持する。

IDがない行は、CSV読取後のrecordsのJSONハッシュ、日付・絶対額・収支種別・厳密な摘要・取込元・口座、同じ条件内の出現順で`csv2:`キーを作る。同じファイルを同じ割当で再取込すればキーが変わらない。ファイル名は含めない。UTF-8/BOM/Shift_JISや改行だけの違いは同じrecordsとなる。行追加・削除・並び替え・表記変更は別ファイルになるが、既存の支出としても新しい支出としても無根拠に確定しない。

## 不明な場合の確認

fingerprint/aliasが一致しない行は同じファイルでも候補を確認する。安定ID列の追加・解除や取込元・口座の大小文字変更で別キーになっても、同ファイルだから新規明細とは判断しない。

別ファイルに、同じ所有者・取込元/口座・日付・金額・収支種別の候補があればプレビューで質問する。取込元/口座の大小文字差を候補検索で考慮する。摘要が完全一致しなくても、大文字・空白・店舗末尾などの表記差や、同日同額の別店舗を候補から落とさない。既に別々の安定IDが検証済みなら、そのIDを根拠に別明細として保存できる。

画面ではCSV行番号、入出金、額、摘要と既存候補のID・摘要・カテゴリを表示する。各行を「この既存明細と同じ」または「別の新しい明細」として明示確認し、再プレビューする。未回答があればpreview_idを発行せず、確定も拒否する。同じ既存明細を同一ファイルの複数行に割り当てられない。存在・所有者・対象条件に合わないIDは拒否する。

sameの確認にはプレビューで取得した候補snapshotを添える。ID・日付・額・収支種別・摘要・取込元・口座の不変を確定時に再検証し、分類訂正はsnapshotから除外する。表記違いをsameと確認した場合も元の摘要・raw record・分類・日時は保持する。対応したincoming内容と既存snapshotをaliasに保存し、同じCSV再取込では確認結果を再利用する。既存内容が後で変わっていたらaliasを無条件に使わない。

候補は書込前に取得する。一つの旧行を先に引き継いだ結果、後続の未回答行の候補が消えて自動追加されることを防ぐ。確定はプレビューの判断を信用するだけでなく、同じトランザクション内で再検証する。並行取込で確認が先に確定した場合、矛盾する判断は採用しない。

owner/file/大小文字を統一したsource/account/収支種別の範囲で、物理行番号と保存明細IDをcsv_identity_file_rowsへ一対一で保存する。行から明細、明細から行の双方をDB一意制約で保証する。aliasの複合FKで、同じ行の別strategyキーだけを同じ明細へ結ぶ。同じ行をdistinctで別明細へ追加することも拒否する。別口座・取込元・収支種別は別scopeとして保存できる。行番号はCSVの物理行で、ヘッダー後は2から数える。別fileの行対応は独立する。旧行も明示確認時に対応を保存する。行対応はキー・aliasと同じtxで保存し、再起動後も保持する。このmetadataはLLMへ送信しない。

既存fingerprintやaliasで重複と判断した場合も、取り込んだCSVごとに物理行対応を同じtxで検証・保存する。別CSVの安定IDで重複除外したあと、そのCSVのID列を変更・解除しても行対応を失わない。既知物理行の保存明細はIDの違いだけで候補から除外せず、same確認の対象として示す。既知行のdistinct追加と確定済み内容との矛盾はpreview・commitの双方で拒否する。previewだけでは行対応を保存しない。

## 旧キーの移行

PostgreSQL012とSQLite006は既存行・row ID・所有者・分類・原文を保持し、identity_versionを1として移す。旧キーは収支種別や出現数を表現できず、欠落した正当な行はDBだけから復元できない。

旧行には確かなfile identityがないため、同条件でも自動で再利用しない。元CSVの再取込で「既存の1行と同じ」「不足していた行は別」と確認した時点で、その旧行を一度だけversion2へ引き継ぐ。row IDとカテゴリ訂正を保持し、元fingerprintはlegacy_fingerprintへ残す。不足行だけを追加し、その後の再取込はaliasで重複除外する。旧入金が支出へ変わることもない。

PostgreSQLは所有者ごとのadvisory lockで確定を直列化し、同一候補の内容確認時には行をロックする。SQLiteはテスト用で、旧global fingerprint uniqueを所有者付き制約へ置き換え、chat_transaction_ownersを維持する。006はFKを接続上で一時無効化し、BEGIN IMMEDIATE内でversion確認・テーブル再構築を行い、成功・失敗ともFKを戻す。所有者未割当の旧行は暗黙に割り当てない。保存・キー引継ぎ・aliasは一つのtxで、失敗時は全件rollbackする。SQLiteの競合エラー時は再プレビューし、確定済み結果を読み直す。

## HTTP契約と保証の範囲

`POST /transactions/import/preview`のmultipartへ従来のsource/source_account_name/mappingに加えて`identity_decisions`のJSON配列を送る。各決定はrow/action/transaction_id/snapshot。mappingの任意transaction_id_columnは列名。応答のidentity_conflictsはrow/transaction/candidates/candidate_snapshots、identity_noticeは案内。候補にraw_dataを追加送信しない。snapshotのキーは候補IDの文字列。

プレビューは保存せず所有者と30分期限を持つ。確定は従来のpreview_idを使い、imported_countは新規行、duplicate_countは既存行との対応と再取込を数える。プレビューのメモリは再起動で失われるが、確定したaliasはDBに残る。保存失敗は成功表示にせず、再プレビューを案内する。

情報のない別期間CSVの完全自動照合や、名前変更した実口座の推定は保証しない。本人の明示確認を根拠に記録する。#111のチャット購入との照合、#34の全取込取消し・一般的な監査、#5の全CSV形式対応を含めない。新チャットの残高計算はLLMが担い、Goへ移さない。LLMの取引DTOは日付・金額・カテゴリのみで、merchant/account/raw/取引ID/確認snapshot/aliasを追加しない。

## 検証
