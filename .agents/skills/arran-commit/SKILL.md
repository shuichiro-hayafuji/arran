# Arranのコミットとpush

レビューしやすく、各コミットを取り出してもビルドできる履歴を作る。ユーザーの明示的な指示を優先し、実際に確認した範囲と未確認の範囲を分けて報告する。

## 作業範囲とブランチ

- ルートの`AGENTS.md`、`docs/harness/INDEX.md`、`tools/INDEX.md`を読み、変更対象の検証方法を選ぶ。日本語のメッセージにはjapanese-editorを適用する。
- `git status --short`、現在のブランチ、remote、upstream、ステージ済み・未ステージの差分を確認する。既存の変更やステージ状態を自分の作業と決めつけない。
- リンクするIssueがある場合、ブランチ名は`feature/<Issue番号>`とする。例は`feature/17`。複数Issueの場合は作業の主対象を使い、主対象が判断できない場合だけ確認する。番号を推測したり、命名のためだけにIssueを作ったりしない。
- Issueがない場合は`feature/<短い英語の作業名>`とする。ユーザーがブランチ名を指定した場合はその名前を優先する。
- 同名ブランチがあれば履歴と用途を確認し、同じ作業なら再利用する。別作業なら上書きせず、衝突を報告する。既存のリモートブランチを削除・改名して合わせない。
- 新規ブランチの起点は指定されたbaseを使い、指定がなければ対象PRや既定ブランチから判断する。現在のHEADを無条件に起点とせず、別作業の未マージコミットが混入しないか確認する。既存の変更を保持できない切り替えは避け、必要なら隔離したworktreeを使う。

## コミットを分ける

- 一つのコミットは一つの関心ごとにする。先に各コミットの目的、含める変更、依存順序、検証方法を決める。ファイル数や行数だけで分割しない。
- 各コミットは、それ以前のコミットを含む時点でビルド可能にする。後続コミットや未追跡・未ステージのファイルがないと成立しない分割をしない。
- 振る舞いの変更と、その変更を保証するテストを同じコミットに含める。必要な型・呼び出し元・生成物・設定・依存定義も合わせる。既存動作のテスト追加だけで成立する場合は先に分けられる。
- 大きなリファクタリング、機械的な整形、機能追加、独立した不具合修正は分ける。ただし、分けるとビルドや動作が壊れる変更は一緒にする。小さな関連修正を無理に細分化しない。
- 文書だけのコミットにはアプリのビルドを一律に要求せず、リンクや内容の整合性を確認する。

## 日本語のコミットメッセージ

- 件名は「何をどう変えるか」を日本語で簡潔に1行で書く。例：`CSV取込時の重複登録を防ぐ`。「修正」「対応」「更新」だけで終わらせない。
- 識別子や正式名称は原文を保つ。英語の接頭辞や文字数制限を必須にせず、履歴一覧で変更を理解できる短さを優先する。
- 件名だけでは理由・影響・制約が伝わらない場合、空行の後にサブメッセージ（本文）を日本語で追加する。変更理由、従来との差、重要な判断や未検証事項を必要な範囲で書き、差分の逐語的な説明は避ける。
- 関連Issueは必要に応じて本文末尾に`Refs #17`のように記載する。マージ時のIssue自動クローズはPR本文の`Closes`で管理し、[PR用Skill](../arran-pull-request/SKILL.md)に従う。

例（架空の変更）：

```text
CSV取込時の重複登録を防ぐ

同じ明細を再取込すると支出が二重計上されるため、
確定済みの明細を照合して重複分を登録対象から除く。

Refs #17
```

## ステージと検証

- 対象パスを指定してステージし、同じファイルに別の関心ごとが混ざる場合は部分ステージを使う。差分の確認なしに`git add .`、`git add -A`、`git commit -a`で取り込まない。他者のステージ済み変更が混ざる場合は、その状態を保持したまま分離する方法を選ぶ。
- `git diff --cached`と`git diff --cached --check`でコミット対象そのものを確認する。秘密情報、ローカル設定、一時ファイル、意図しない生成物を含めない。読み取りを禁止されたファイルを検査のために開かない。
- `python3 tools/harness.py check <scope>`を対象に応じて実行し、必要なビルドコマンドがscopeに含まれない場合はプロジェクトで定めたビルドも実行する。最終状態だけの成功を途中の各コミットの成功としない。
- 部分ステージや複数コミットへの分割では、コミット予定のスナップショット、または作成した各コミットを隔離した作業ディレクトリで検証する。未コミットの残りを含む作業ツリーだけの成功では不十分。ユーザーの変更を一時退避・破棄して検証環境を作らない。
- ビルドやテストが変更原因で失敗したら修正または分割を見直し、失敗したままpushしない。環境不足などで実行できない場合は未検証と明記し、ビルド可能と断定しない。未検証状態での公開が依頼範囲に含まれなければ、ローカル作業を残してpush前に確認する。
- 既存のGit hookを尊重し、失敗回避のために`--no-verify`やhook無効化を使わない。hookがファイルを書き換えた場合は差分とステージ内容を再確認し、変更に応じて再検証する。
- メッセージ本文は一時ファイルと`git commit -F`等で渡す。文章をシェルコードへ直接埋め込まない。作成後はSHA、メッセージ、コミットの差分、残る作業ツリーを確認する。

## push

- commitのみの依頼ではpushしない。pushを依頼された場合は、送信先remoteとブランチ、送信予定の全コミットを確認する。新規リモートブランチではbaseとの差分も確認し、過去の別作業を巻き込まない。
- 送信先の最新状態をfetchして比較する。通信に失敗したら、古いリモート追跡情報を最新と扱わない。fetchは作業ツリーへのmergeを意味しない。
- 初回は`git push -u <remote> <branch>`などで送信先と対象ブランチを明示する。通常のpushでも対象を明示し、`--all`、`--mirror`、不要なタグ送信を使わない。
- non-fast-forwardで拒否された場合はfetchして差分を確認し、他者のコミットを保持して統合する。未公開の自分のコミットは必要に応じてrebaseできるが、公開済み履歴の書き換えは明示的に依頼された場合に限る。統合後は影響する検証を再実行する。
- 公開済み履歴の書き換えを依頼された場合も、通常の`--force`は使わず、確認したリモートSHAを指定する`--force-with-lease=refs/heads/<branch>:<確認済みSHA>`で対象を限定する。lease不一致なら停止して再確認し、期待SHAを機械的に更新して再試行しない。
- push後は`git ls-remote <remote> refs/heads/<branch>`等でリモートのSHAと送信したSHAの一致を確認する。不一致や再取得失敗は確認未完了と報告する。通信結果が不明な場合はまずリモートを確認し、同じ操作を無制限に繰り返さない。
- 完了時はブランチ名、各コミットのSHAと件名、検証結果、pushの成否、残した差分を報告する。PR作成は依頼された場合にPR用Skillへ引き継ぐ。
