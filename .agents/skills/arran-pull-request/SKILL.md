# ArranのPR作成・更新

この会話を知らないレビュー担当者が、変更の目的、動作、検証結果、残る判断を本文から理解できるようにする。

## 対象と根拠を確かめる

- 対象リポジトリのルートを確認し、ルートの`AGENTS.md`と`docs/harness/INDEX.md`に従う。日本語にはjapanese-editorを適用する。
- `git status`、remote、現在のブランチ、PRのbase/head、コミットと差分を確認する。baseを`main`と決めつけない。既存PRがあれば本文、コメント、レビュー指摘、チェック結果を取得する。
- PRへ入る差分と未コミットの変更を区別する。未コミット・未pushの変更を公開済みPRの内容として説明しない。作成時は同じhead/baseのPRがないか確認する。
- 検証は`tools/INDEX.md`の入口を使い、対象のコミットや作業ツリーと実行結果を対応づける。以前の成功を変更後の成功として流用しない。

## レビューしやすい範囲に整える

- 一つのPRは一つの目的で説明できる範囲にする。関連テスト・必要な文書・設定は同じPRに含め、大きな整形やリファクタリング、独立した機能は分ける。行数だけの上限は設けない。コミットを分けただけでPR全体がレビューしやすくなったとは判断しない。
- 依存するPRがある場合は依存先、base、マージ順を明記し、レビュー対象の差分を区別する。各段階で動作が成立する分割を選び、依存PRのマージ後はbaseと差分を再確認する。
- 投稿前に差分全体を自分で読み、目的外の変更、不要な複雑さ、境界条件、失敗時の挙動、必要なテスト・文書の不足を確認する。自分の確認をレビュアーの承認として扱わない。
- 実装途中、重要な設計が未決定、必須検証の失敗・実行不能など、レビュー完了を判断できないPRを公開する場合は、ユーザーの指定がなければDraftにする。理由とレビュー可能にする条件を本文に書く。通常の未確認事項すべてをDraftの理由にはしない。

## テンプレートで本文を作る

正本はリポジトリルートの[PRテンプレート](../../../.github/pull_request_template.md)。毎回実ファイルを読み、案内コメントを具体的な内容に置き換える。

- タイトルは最終的な変更を簡潔に示す。本文の見出しを維持し、小さな変更は各項目を短くする。作業中の会話や採用しなかった案は、判断理由として必要な場合だけ書く。
- 本文だけで「何を、なぜ変えるか」が分かるようにし、Issueや設計資料のリンクだけで説明を済ませない。重要な制約やトレードオフは短く残す。UIや操作の変更では、理解に役立つ再現手順や画像を必要に応じて添える。
- 検証結果には実行コマンド・結果・確認範囲を書く。FAIL、BLOCKED、未実行を成功へ言い換えない。CIとローカル検証を区別する。
- レビュアーの確認項目は未チェックで作成する。変更に関係する設計・境界条件・テストの妥当性などを具体的なチェック項目にし、該当しない観点を一律に並べない。既存のチェック状態は保持し、差分変更で再確認が必要な点は新しい未チェック項目にする。
- 認証、ユーザー間のデータ分離、金額、DB、AWSへの影響がある場合は、該当する変更のリスクや失敗時の挙動を説明する。関係のない注意書きを一律に追加しない。
- 関連Issueがある場合は、マージ時に自動クローズする方針に従い、PR本文へIssueごとに`Closes #番号`を書く。別リポジトリなら`Closes owner/repo#番号`を使う。ユーザーが参照のみと指定したIssueは`Refs`にする。完了条件が未達・不明なら、その内容を未確認事項とレビュアーの確認項目へ明記する。
- 自動クローズはデフォルトブランチへのマージ時に有効なため、対象リポジトリのデフォルトブランチとPRのbaseを確認する。異なる場合は、そのPRのマージだけではクローズされないことを報告し、baseの変更やIssueの手動クローズを勝手に行わない。
- 更新時は人が追記した判断や未解決事項を保持し、古くなった説明と検証結果を現在の差分に合わせる。投稿直前に現行本文を再取得し、他者の追記を上書きしない。

## 必要なコメントを選ぶ

本文は現在の変更内容の正本とする。コメントは、レビューへの回答、指摘の修正結果、投稿後の追加検証、判断が必要な変更の通知に使う。本文の全文転載や作業実況だけのコメントは追加しない。

- レビュー指摘への回答は、対応するスレッドへ返信する。対応内容、根拠となるファイルやコミット、検証結果、未解決点を必要な範囲で示す。
- 「分かりにくい」という指摘には、まずコード・命名・文書を改善し、必要なら理由をコードコメントに残す。返信だけに将来の保守で必要な説明を閉じ込めない。異論がある場合は根拠とトレードオフを説明し、未合意の点を対応済みにしない。
- 自分がレビューする場合は、修正が必要な問題と任意の提案（Nit）を区別し、個人的な文体の好みだけでマージを妨げない。確認した範囲を明示し、CI成功だけで設計やテスト内容まで正しいと判断しない。
- 全体に関わる追加情報は通常のPRコメントへ書く。行へのコメントが必要なら、最新diffの有効な行とsideを確認する。
- 投稿前に既存コメントを読み、同じコミット・同じ結果の重複投稿を避ける。既存コメントの編集はCodexが作成した対象に限り、他者の発言は変更しない。
- 本文を変えた事実だけではコメントを増やさない。再通知する意味がなければ本文の更新だけで終える。
- 修正後は変えた点と再検証結果を伝え、必要な箇所の再レビューを依頼する。pushや返信だけで相手の承認が得られたとは扱わない。実装への指摘の記録・再発防止は`docs/harness/FEEDBACK.md`に従う。

## GitHubへ反映する

ユーザーがPRの作成・更新・レビュー対応を依頼した範囲で投稿する。このSkillを明示的に使ったPR作成・更新依頼では、上記の必要な補足コメントも対象に含む。「本文だけ」「下書きだけ」の依頼では投稿せず、ローカルの本文を渡す。Skill自体の作成依頼は、実際のPR投稿依頼として扱わない。

- 利用可能なGitHub接続か`gh`を使う。複数行の本文・コメントは構造化引数、または一時ファイルと`--body-file`で渡す。未信頼の本文をシェルコマンドへ埋め込まない。
- 作成時は対象repo、base、headを明示する。公開前に必要なcommit/pushは依頼された差分だけを対象とする。無関係な変更の取り込み、force push、mergeはこのSkillの作業範囲に含めない。
- ブランチ作成・commit・pushが必要な場合は[arran-commit Skill](../arran-commit/SKILL.md)を読み、命名・分割・検証のルールに従う。
- GitHubへの書き込みが失敗したら本文・コメントの下書きを残す。結果が不明な場合は対象PRやコメントを再取得し、成功した操作を重ねない。権限や接続の問題が続く場合は再試行を止め、未反映の操作と原因を報告する。
- 投稿後は本文・コメントを再取得して内容と対象を確認する。PRを作成した場合、Codexの`attach_artifact`が利用可能ならURLを現在のタスクへ添付する。
- 完了時はPRのURL、反映内容、実際の検証結果、未反映・未確認事項を簡潔に報告する。コメントを投稿した場合は、このSkillの使用とリンクも示す。
