# チャット主体の支出相談要件

関連: [Issue #20](https://github.com/shuichiro-hayafuji/arran/issues/20)、[対象者と支出相談の体験](target-users.md)、[初版の提供範囲](initial-release-scope.md)

2026-09-28の対話で確定した目標要件。要件定義の完了を示す文書であり、実装済みの動作を示すものではない。現在のGo serverは金額計算と最終判定を担い、プロフィール画面などからも情報を入力するため、本書の責務分担と操作は未実装である。

## 背景と目的

対象者は、お金の計画や管理が苦手で、入力項目を埋めたり定期的に情報を更新したりすること自体を負担に感じる。Arranは、利用者が支出について自然に話せば、過去の会話や記憶も踏まえてLLMが助言できる体験を目指す。

プログラムで利用可否を機械的に制限したり、固定条件に違反したことを理由に相談や支払いを止めたりしない。プログラムは会話の文脈を適切に残してLLMを支え、LLMは金額、目標、嗜好、状況を総合して助言する。

## 確定した要件

### 入力と利用

- 利用者との入出力はチャットだけで完結させる。金融情報の入力フォームや記憶管理画面を利用条件にしない。
- Arranは助言を返すが、条件違反を理由に相談や支払いを禁止しない。支出先を道徳的に評価せず、お金の状況と本人の目標・嗜好に照らして答える。
- 予定された更新作業や定期入力を求めない。判断に影響する情報が必要なときだけ、会話の流れで確認する。

### LLMとプログラムの責務

- LLMは、金額の計算、発言の解釈、貯蓄目標や嗜好を含む総合判断、利用者への助言を担う。
- プログラムは、会話履歴、記憶、嗜好、過去の助言を保存し、相談に関係する情報だけを検索してLLMへ渡す。
- プログラムは固定の金額計算や最終判定を行わない。`safe`や`avoid`などの固定区分を必須にせず、LLMが会話に合う短い結論を返す。
- この責務分担は目標状態である。既存のGoによる金額計算・最終判定は、後続Issueで移行方法と検証を定めて変更する。

### 記憶と検索

- LLMが会話から将来の相談に役立つ情報を選び、確認操作を挟まずに記憶する。利用者は後からチャットで訂正・削除できる。
- 利用者が述べた事実と、LLMが会話から推測した内容を区別して保存・提示する。推測を事実として扱わない。情報源と記録時点をたどれるようにし、推測には必要に応じて根拠と確からしさを持たせる。
- 「忘れて」と依頼された情報は会話履歴に表示されたままでもよいが、以後の検索、LLMへ渡す文脈、再推論の根拠から除外する。
- 新しい相談では、関係する過去の発言と整理済みの記憶だけをLLMへ渡す。無関係な情報と削除対象は渡さない。
- 情報が更新された場合は最新の内容を通常利用し、古い内容は変更の経緯として保持する。古い情報は経緯が必要な場合だけ参照する。

### 不足・矛盾・古さの扱い

- 固定の有効期限や必須確認項目は設けない。LLMが助言への影響を判断する。
- 影響が大きい場合だけ、会話の中で自然に確認する。影響が小さい場合は、不確かさや置いた前提を区別して暫定的に答える。
- 事実、利用者の発言、LLMの推測を回答でも混同しない。

### 回答と失敗時の動作

- 最初に「今回は見送りを勧めます」「この点だけ確認したいです」「使ってもよさそうです」のような、短く実行しやすい結論を返す。表現は固定の判定値に縛らない。
- 詳しい赤字額を最初から並べず、罪悪感を与えない言葉で状況と理由を伝える。
- 通常は生成した回答を表示する。LLMが不確かさや影響を大きいと判断した場合は、表示前に自ら矛盾や計算を見直す。
- LLM呼び出しに失敗した場合は回数を限定して再試行し、設定されていれば別のLLMも試す。すべて失敗した場合は、今は助言できないことを伝え、相談内容を失わず再試行できるようにする。プログラムが代わりに金融判断を返さない。

### 外部LLMへ送る情報

- 認証情報、パスワード、口座番号・カード番号の全桁は外部LLMへ送らない。
- それ以外は、相談への関連性と必要性がある利用者入力を送信できる。相談と無関係な履歴や、忘れるよう指定された情報は送らない。

## 利用例

利用者が「今月ライブへ行きたい。前に話した旅行の貯金も続けたい」と送る。プログラムは旅行の目標、関係する収支の発言、直近の助言を検索してLLMへ渡す。LLMは必要なら金額を計算し、目標とライブへの希望を総合して短い結論と理由を返す。

情報が矛盾して結論に大きく影響するとLLMが判断した場合だけ、「先月は残高が5万円と聞きましたが、今も近いですか」のように確認する。影響が小さければ、置いた前提を示して回答を続ける。利用者が「旅行の予定は忘れて」と伝えた後は、その情報を以後の検索や判断に使わない。

## Issue #20の完了範囲

Issue #20では、本書によって対象者、相談体験、責務分担、記憶、失敗時の動作、外部送信の境界を確定する。コード、画面、データ構造、プロンプト、モデル切替の実装は含めず、実装単位ごとに後続Issueへ分ける。

全回答を毎回LLMで見直す方式は、初版の要件には含めない。費用と待ち時間を確認したうえで導入を判断するP3課題として管理する。

## 確認済みの事実と未検証事項

確認済みなのは、開発者本人との対話で上記の製品方針を選択したことまでである。対象者が実際にチャットだけで必要な情報を伝えられるか、LLMの計算・判断が十分に正確か、記憶の検索・削除が期待どおり機能するか、外部LLMへの送信範囲が法務・セキュリティ要件を満たすかは未検証である。

実装後は、事実と推測の分離、忘却後の検索除外、無関係情報の除外、失敗時に金融判断を捏造しないこと、相談結果の品質をそれぞれ検証する。
