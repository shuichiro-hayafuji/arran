# FB-20261125-05: 退会と進行中 DB 書込みの停止境界

- 発生日・最終更新日: 2026-11-25
- 状態: 対応中
- 対象領域: 退会受付・日次バッチ・DB 接続寿命
- 関連ルール: [B-S06](../../server/business.md)、[C-S07](../../server/conventions.md)
- 出典: 進行中 HTTP 操作と接続断の独立確認

## 指摘と対応

認証後に始まった書込みはセッション失効後も処理を続行し得る。別接続に advisory lease を保持するだけでは、その接続が落ちてロックが解除された後も実際の書込み接続がコミットし得るため、停止の保証にならない。認証済み本人の行ロックと書込みを同じ PostgreSQL トランザクションで行う未接続の試作部品を追加した。トランザクション接続を強制終了すると書込みは rollback され、成功も返らない。

独立レビューで、接続強制終了自体の失敗でも回帰テストが成功し得ることと、開始通知の待機が無期限になり得ることを指摘された。強制終了の呼出し・成功・callback の正常終了をそれぞれ確認してからコミット失敗を検証し、開始・終了待機に期限と先行エラーの検出を加えた。待機中の callback はテスト終了時にも解放する。試作 callback には Commit を公開しない専用 interface を渡す。

## 検証と残り

プロフィール・記憶・月次レビューに試作を限定適用し、実 DB で本人の通常更新・削除、他人による更新・削除拒否、退会申込中の変更拒否とレビュー件数維持を確認する回帰を追加した。独立レビューで通常更新・削除と申込中レビューの残存検査が不足していたため追加した。CSV 確定・プレビュー保存・訂正・購入照合・相談結果更新・相談取消にも同一 transaction の本人状態ロックを適用する。CSV は会員行から所有者 advisory lock の順で取得し、チャット保存とのロック順を合わせる。

独立レビューで、DB既定が REPEATABLE READ のとき、会員行のロック待ち後に古い snapshot の退会状態を参照する可能性を指摘された。本人状態を再確認する transaction は READ COMMITTED を明示し、既定を REPEATABLE READ にした実 DB で受付が先に commit する競合を検証する。また、応答途絶後に退会を申し込んだ本人が確定済みCSVの結果を再取得できなくなる指摘に対し、有効な本人に限り通常・0行の既存receiptを読み取れるようにした。未確定の新規確定、他人・無効会員の読み取りは拒否する。

隔離 PostgreSQL で別接続からの受付待機、実トランザクション接続の強制終了、親 HTTP 文脈取消後も残る模擬 worker、1 接続 pool の枯渇と復帰を確認した。ただし専用 interface でも callback が別接続や他の所有者へ書き込むこと、外部副作用を起こすことは防げず、同一 package 内での内部アクセスも制限できない。上記の限定的な repository 操作を除き、既存 HTTP 全操作・ReminderWorker・外部 AI を網羅していない。残りの repository の所有者制約、トランザクション境界とロック順、切断・結果不明、運用・復元時の独立証跡を改めて検証する。退会受付は強制停止を維持する。

独立レビューで、AI同意の送信直前にログインが切り替わると別会員の認証情報を使い得ること、未知の409応答を確定拒否として扱うことを指摘された。PUT・DELETEとも開始時のセッション世代を通信層へ渡し、送信直前に照合する。既知の `withdrawal_pending` と `consent_not_granted` のみ固定文言で表示し、それ以外は再取得しても結果不明として扱う。Flutter の同意・CSV関連33テストと Go handler テストが通過した。外部送信や通知を退会受付と直列化する永続 marker は未実装であり、強制停止解除の根拠にはならない。

独立レビューで、通知の開始と退会を直列化する必要、送信後の結果不明を再送成功で消せないこと、確実な未送信との区別、移行済みDBへの新規マイグレーションが指摘された。通知の取得を本人ロックと同一 transaction にし、送信中・不明結果を退会から遮断する。確実な未送信は明示型で区別し、既存の単発成功は移行時に安全とする。完了記録に失敗した場合は機密を含まない固定文言で通知し、更新0件も失敗として扱う。実DBの権限・移行・競合回帰と通常テストを追加した。

同期相談の予約には操作IDを持つ永続 marker を追加した。利用回数の増減と marker の遷移をそれぞれ同一 transaction にし、同IDへの再試行は開始権を与えず、重複返却は同じ結果で完了する。commit応答不明の active marker を安全に回復する方法は未実装である。新規・継続の同期チャット経路に接続し、明示的に副作用前と証明された失敗だけを返却する。実 DB での経路競合と独立証跡は未検証・未完了であるため受付・バッチは引き続き強制停止する。

モデル呼出後の同意拒否などが確実に未送信だったかは、複数回試行を含めて同期相談の呼出元へ証明できない。その場合は保存が rollback されても予約 marker を保持し、現時点で自動解除しない。運用での調査・解消手順は未整備である。

外部AIの利用量記録は、送信 marker の解消後に独立 context で書き込まれる経路が残る。marker 解消前に移す案は、確定的な記録失敗でも回答や同意撤回を不当に止めると独立レビューで指摘され、適用を取り消した。記録の操作IDと結果照合、確定失敗と commit 不明の区別が未実装のため、退会受付・バッチの停止を継続する。

利用量については送信処理と会計結果を分離する未接続の試作を作成した。prepared から sending の commit を確認した場合だけ送信 callback を呼び、未確認なら送信しない。sending で結果不明のものは保留し、確定した利用量は本人と操作ID単位で staging・照合する。usageなしの応答を外部証拠で確認する経路、OpenAI実送信・再試行への接続、復元の独立証跡は未完成である。
送信開始記録に失敗した場合は prepared の未送信完了を短時間だけ試みるが、その cleanup 自体の結果不明を再起動後に照合する運用は未整備である。
