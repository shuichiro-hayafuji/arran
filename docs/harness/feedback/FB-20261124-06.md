# FB-20261124-06: 復元時の台帳と利用者スナップショットの境界

- 発生日・最終更新日: 2026-11-24
- 状態: 対応中
- 対象領域: 退会削除・独立台帳・復元照合
- 関連ルール: [C-S07](../../server/conventions.md)、[サーバー構成](../../server/architecture.md)
- 出典: 2026-11-24 Astra 6.2 medium 独立レビュー

## 指摘と根拠

- 期待する結果: 読取失敗や取得漏れを空のスナップショットと見なさず、本人識別を守りながら同じ username の異なる利用者の順次退会にも対応する。
- 実際の結果: 台帳照合候補が nil の利用者一覧を正規の空一覧と区別せず、異なる ID による同一 username の再利用を一律に拒否した。
- 確認済みの事実: 読取失敗を示す nil は正規の空一覧ではなく、利用者名が異なる ID に再利用され得るため、ID・username・作成時刻を合わせて照合する必要がある。
- 未確認事項: 信頼できる独立台帳、最新性と真正性の確認方法、復元時の一貫した DB 読取は未実装。実際のバックアップ復元・再適用は未検証。

## 原因と対応

同一性と失敗状態を単純化して計画部品に与えており、失敗時のゼロ値と正常な空コレクション、利用者名の再利用を区別する契約が不足した。nil の台帳と利用者スナップショットを拒否し、同一 username の別 ID は、復元時の利用者が別の完了済み台帳上の ID・username・作成時刻と一致する場合に限って扱う。対応関係が不明なら拒否する。

空チェックポイント・空スナップショット、欠損、異なる本人、ID 再利用、同名の順次退会、複数の準備・完了の交差、途中の未完了、検証済み head と不正 previous の組合せを純粋 Go テストで確認する。既存の本人境界と DB 整合性ルールの適用であり、共通ルールの追加は不要。

この部品は外部台帳・DB 読取・復元処理・公開制御に接続していない。ハッシュ連鎖自体は真正性と鮮度の証拠にならず、未取得を空として渡さない実運用上の強制手段が必要である。

再レビューでは、台帳自体の nil も未取得として拒否する必要と、先行する完了済みの本人が復元データに存在しても後続の未完了があれば部分計画を返さないことを指摘された。双方について独立した回帰を追加した。台帳 nil の検証では、件数不一致による拒否で隠れないよう、正常な空 head・非nil 空利用者一覧を与える。
