# FB-20261012-04: 購入履歴の送信量と再申告の冪等性

- 発生日: 2026-10-12
- 最終更新日: 2026-10-12
- 状態: 完了
- 対象領域: server、購入確認、外部送信
- 関連ルールID・正本: B-S08、B-S10、C-S04、C-S05、[相談の送信・保存境界](../../../server/docs/chat-consultation.md)
- 出典: Issue #22実装中のmain sessionによる確認。購入・イベントの無制限送信、金融記憶補充時の全項目の除去、同じ実績の再申告による二重計上防止を指摘。

## 指摘と根拠

- 期待: 複数購入でも外部送信を最小限に制限し、既に保存した実額・分類・結果の再申告でイベントと残高反映を重複させない。
- 確認した事実: 初稿のmodelPurchasesは全購入と全イベントを送っていた。financialFactsの補充経路ではKeyの除去処理が未明示だった。同じ確定結果のpurchase_updates再出力を拒否する検証がなかった。
- 未確認: 実LLMの解釈・計算品質と実機表示。制御モデルの回帰はこれらの保証ではない。

## 原因と対応

- 原因: 複数保存と時刻・トランザクションの検証を先行し、既存の文脈取得量制限と再申告の更新単位を回帰へ含めていなかった。
- 修正: 確認待ち優先で最大20件、関連する完了済みまたは現在相談の履歴を最大6件、イベント最大6件、JSON全体16000バイトへ制限し、未取得数・部分取得を送る。イベントは最新の計上済み結果を含める。金融記憶の補充もKey・Value・Source・Periodを除去する。
- 冪等性: 購入IDと最新の計上済み結果・実額・分類が同じ更新は不正出力として再試行する。モデルが更新なしへ修正した応答を採用し、重複イベントと再減額を保存しない。Goへ金融計算は追加しない。
- 正本: 相談文書に取得上限、部分取得、変化のない申告を更新しない契約を記載。
- 回帰: 40件の予定と20イベントでサイズ・件数上限、関連する過去実績、除去処理を確認。同じ購入の再申告と同額訂正では、誤った二重投稿を拒否して再試行し、イベント数と残高・自由予算が維持されることを確認。
- 修正前のFAIL: 初稿に対する新規回帰の実行記録は未取得。実装経路の確認に基づき修正した。
