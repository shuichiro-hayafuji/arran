# FB-20261124-03: 外部AI同意の復元とデータ取扱いの記載

- 発生日・最終更新日: 2026-11-24
- 状態: 対応中
- 対象領域: 外部AI送信同意、DB復元、データの棚卸し
- 関連ルール: B-S06、C-S07
- 出典: PR #137 の独立レビュー

## 指摘と根拠

過去時点のDB復元では後の撤回や未完了の送信記録が消え得る。GETだけでは撤回保留は解除されない。端末保存・ホストsnapshotや旧相談・月次・記憶抽出の送信項目、月次候補ラベルの情報混入可能性の説明も不足していた。

## 原因と対応

復元後の同意と送信記録の整合、保留の再実行、送信データ経路ごとの境界を運用資料と棚卸しで十分に区別していなかった。復元後の送信停止と独立証跡による照合を必須とし、根拠がない場合は停止を維持する。本人による撤回再実行と、端末・snapshot・各送信経路の情報を明記する。照合方法と実環境の確認は未整備として残す。

追加レビューで、月次候補のラベルに含む文字列による安全判定では加盟店名を漏らし得ることが判明した。外部送信境界で由来の推測をやめ、全ラベルを番号付き代表表現に置換し、元のローカル候補を保持する。HTTP送信payloadを使ってカテゴリと加盟店由来の候補を回帰確認する。モデルの回答にも代表ラベルが現れ得る。また「忘れて」の対象を新チャット文脈に限定して明記する。

再レビューでOpenAI送信境界だけの置換では独立Agentへ生のラベルが渡ると判明した。ApplicationからAgentへの受渡し前にも番号付きコピーを作成し、ローカルfallbackは元の候補を使う。Agentが受け取るDTOとHTTP payloadの両方を検証する。

mockや外部モデルの通常エラー時に独立Agent内で生じるfallbackは正常応答と区別できず、代表ラベルが表示され得た。adapterがローカル応答と内部fallbackを明示し、Applicationが元の候補を採用する。同意拒否・結果不明はfallbackに変換せず、外部応答には元ラベルを推測で対応付けない。

## 検証と判定

`python3 tools/harness.py check docs`・`check server`、差分検査はPASS。Astra 6.2 mediumの独立レビューで指摘を修正し、再レビューで追加のP1・P2はなかった。統合レビューで、#139で追加された未確認CSVプレビューIDの端末保存も一覧に追記した。実際の復元、独立証跡の確保・照合、OpenAI契約、本番の保持設定や端末動作は未検証。
