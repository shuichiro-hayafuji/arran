# FB-20261124-04: 退会申し込みの本人境界と未確定結果

- 発生日・最終更新日: 2026-11-24
- 状態: 対応中
- 対象領域: 退会申し込み・認証・DB権限・API契約
- 関連ルール: [B-M02](../../mobile/business.md)、[C-S07](../../server/conventions.md)
- 出典: 2026-11-24 Astra 6.2 medium の独立レビュー

## 指摘と根拠

退会確認後のアカウント切替で別セッションに送る可能性、PUT応答と再取得状況の表示の矛盾、専用PostgreSQL検証の対象漏れ、runtimeの更新・削除権限、API応答スキーマの欠落を指摘された。

再レビューでは、復元スクリプトが現行grant SQLを旧バックアップへ適用する際、v17のテーブルを無条件に参照するとv16の復元が失敗すると指摘された。

運営確認時刻の追加後、表全体へのINSERT権限が残るとruntimeが受付時刻や確認済み時刻を指定し、未確認の依頼を一覧から隠せると指摘された。

## 原因と対応

確認画面の表示時点のセッション世代をHTTP境界まで渡す設計、受付結果の再取得と不確実性、正規検証入口、DB権限とAPI契約を横断して初期実装時に照合できていなかった。世代をリクエストに渡し、受信済み応答と最新状態の確認失敗・不一致を区別する。専用検証の入口にDBテストを追加し、runtimeからUPDATE/DELETE権限を除外してロール検証を追加。OpenAPIに応答の必須booleanを記載した。既存ルールの適用であり共通ルールの追加は不要。

grant SQLでは対象テーブルの存在を確認してから権限を剥奪し、v16相当の復元とv17移行後に同じSQLを適用するロール回帰を追加した。

表全体のINSERTを撤回し、本人ID列のみのINSERTを許可する。実際の配備SQLを適用したロール回帰で通常の受付・再送が成功し、受付時刻と確認時刻を指定したINSERTは失敗することを検査する。

grant SQL 全体をトランザクション化する。途中エラーで全テーブルへの広い権限が残らないことを専用ロールDBの回帰に追加する。復元手順では退会・削除の独立記録との照合前にAPIを公開しない条件を明記する。

トランザクション境界の回帰は実際のgrant SQLの先頭をpsqlと同じく文単位で実行し、一括Execの暗黙トランザクションでBEGIN欠落が隠れないようにする。広い権限が一旦付与されたことを確認してからエラーを注入し、ロールバック後に残らないことを調べる。
