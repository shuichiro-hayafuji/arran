# FB-20261125-01: 退会受付の追跡と復元後再削除の境界

- 発生日・最終更新日: 2026-11-25
- 状態: 保留
- 対象領域: 退会受付・削除・復元
- 関連ルール: [B-S06](../../server/business.md)、[C-S07](../../server/conventions.md)
- 出典: 2026-11-25 Astra 6.2 medium 独立レビュー

## 指摘と根拠

- 運営者の確認後も削除が完了するまで申し込みを追跡する必要があるが、未確認のみの一覧では確認後に見落とす。
- 申し込み前のバックアップに本人が残る場合、台帳の再削除候補に選ばれても通常の削除処理は申し込み記録の不在を理由に拒否する。
- 想定外の所有者表が `user_id` 以外の列名や外部キーなしで存在し得る。対象表のトリガーやruleも削除動作を変更し得る。
- 事前検査より前に準備記録を残すと、確定的に拒否すべきケースでも結果不明として復旧を要する。

## 原因と対応

一覧の「確認済み」と「削除済み」を混同せず、未削除の全申し込みを列挙する手順とした。真正かつ最新な独立台帳から得た候補に限る非公開再適用部品では、本人 ID・名前・作成時刻を照合し、申込が欠けるか確認前なら申し込み日時を照合して同じ削除トランザクション内で記録を再構成する。異なる日時の既存申し込みは拒否する。対象外を含む想定外の実表・パーティション・foreign table・materialized viewや対象表の利用者定義トリガー・ruleは拒否する。事前検査を準備記録前に追加し、記録後の不明な状態を自動解除せず停止・証拠保全する。

従来の本人境界と DB 整合性ルールを適用するため、共通ルールの重複追加は行わない。DB の列定義全体や独立台帳の真正性・鮮度の証明、運用入口、外部処理の結果不明解消は未整備であり、本番に配線しない。

追加レビューでは、migration 006 の正規 `users_enforce_free_user_limit` も利用者定義トリガーのため、一律拒否すると正規 v17 の削除がすべて止まると指摘された。関係表上の非内部トリガーは、埋込み migration の正規関数本体・名前・所有schema・イベント・更新列・有効状態・実行属性まで一致する単一のトリガーだけ許可する。無効化・SECURITY DEFINER への改変、余分なトリガーは拒否する。従来の障害注入トリガーは新しい guard で先に拒否されるため、隔離ロールから後段 transactions DELETE だけ取り消し、先行する CSV evidence 等の削除後に権限エラーを発生させて rollback と他人のセッション保持を確かめる別テストを追加した。ロール作成権限がなければ当該ケースは skip し、実行済みとみなさない。
