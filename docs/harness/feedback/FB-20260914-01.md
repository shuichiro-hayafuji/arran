# FB-20260914-01: 業務決定Issueの日本語が判断内容を伝えていない

- 発生日・最終更新日: 2026-09-14
- 状態: 保留
- 対象領域: GitHub Issueの業務要件記述
- 関連正本: [WORKFLOW](../WORKFLOW.md)
- 出典: 本会話。エピック#79とサブタスクについて「何を決めたいのか日本語が意味不明」との指摘。

## 指摘と根拠

- 期待: 非技術者が、判断すべき内容と決定後の利用場面を理解できる。
- 実際: [エピック#79](https://github.com/shuichiro-hayafuji/arran/issues/79)と子14件で、監査表の短文・専門用語・内部IDを説明へ転記していた。
- 原因: 項目数と対応関係の構造検証を優先し、日本語としての意味・読み手の理解を検証しなかった。

## 対応・再発防止

ユーザー指定の日本語推敲担当サブエージェントが全15件を改稿し、主エージェントが元の判断事項・完了条件との対応を確認する。例示を決定事項に変えない。現在の優先度・親子関係を保つ。再利用する記述原則をWORKFLOWへ追加する。

## 検証と判定

GitHubから現行15件を取得済み。書き込み用CLIはAPI接続失敗、現在のMCPは読み取り専用。リモート更新は未実行。文章修正のためアプリのテストは対象外。docsリンクと改稿の内容を確認する。

次の行動: 改稿レビュー後、GitHub接続可能な環境でタイトル・本文を反映し再取得する。反映未確認の間は完了にしない。

- 改稿レビュー: 全15件で具体的な問いと完了条件を確認。14子課題のHTML識別子、#20/#49の公開停止条件を保持。一般論の重複注意書きを簡潔化。
- PASS: docsリンク確認、15件の対象一致・識別子・完了条件・公開停止条件の確認、更新ファイルの構文確認。
- BLOCKED: 更新ファイルの読取事前確認はAPI接続失敗。タイトル・本文の書込は未実行。改稿と更新用ファイルは/tmpへ保存し、課題台帳をリポジトリへ再作成していない。


## 原因分析と初稿への反映（2026-09-14）

### なぜ最初にできなかったか

- 監査で見つけた状態の説明を、判断依頼の説明として転用した。登録用原稿では表の短文からタイトルと本文を生成したため、「何が不足しているか」は残っても「何を決めれば進められるか」が抜けた。
- コードを読んだ自分の前提を読み手も持つと扱い、spent、権限同期、予算履歴などを説明せず使った。
- 66件の網羅性・ラベル・対応関係・登録の再現性を優先し、各文章を初見で理解できるか確認しなかった。件数確認と構文確認は意味のレビューの代わりにならない。
- 根拠IDや一律の検証注意書きを加えることで、判断すべき問いより周辺情報が目立つ文章にした。簡潔さを情報の圧縮と取り違えた。

### なぜ今回改善できたか

- 推敲担当へ「非技術者が、何を決めるか・なぜ・何に使うか・完了条件を理解する」という明確な目的を渡した。
- 専門語を具体的な操作へ戻し、金額や場面の例を足した。「spent記録」から「使ったと記録した支出を残予算へいつ反映するか」への変更が代表例。
- 推敲担当が読み手の理解を確認し、主担当が元の実装・調査・検証範囲を照合する分担で、説明の改善と要件の保持を両立した。
- 2026-09-14、ユーザーから「一気に読みやすくなった」との評価を得た。サブエージェントの有無だけで改善の因果が証明されたわけではなく、目的・具体化・レビュー工程の変更が再現可能な要素である。

### 次回への対策と確認

WORKFLOWへ初稿作成と全件レビューを明記し、Indexから直接参照できるようにした。次回は指摘後の推敲ではなく、最初の提出・投稿前に同じ確認を実施する。読みやすさを機械検査できたとは扱わず、不自然な語を禁止するだけのcheckerは追加しない。

今回のユーザー評価は改稿の読みやすさへの評価であり、GitHubへの反映確認ではない。リモート更新未確認のため本記録の状態は保留を維持する。
