# FB-20261115-01: 配備途中の再開とバックアップのrelease不一致

- 発生日: 2026-11-15
- 最終更新日: 2026-11-15
- 状態: 完了
- 対象領域: Lightsail配備スクリプト・バックアップ
- 関連ルールID・正本リンク: [C-I03/C-I04/C-I07](../../infra/conventions.md)、[A-I07](../../infra/architecture.md)
- 出典: 2026-11-15の独立レビュー。初回移行後のS3失敗から再開不能、予定image/旧コンテナimageがDB適用releaseと食い違う2件。

## 指摘と根拠

- 期待する結果: DBと秘密を維持して同じreleaseを再開でき、backupには対象DBに適用したreleaseを記録する。
- 実際の結果・対象コード: [deploy.sh](../../../infra/operations/deploy.sh) はinitialの既存schema拒否とupdateの旧API必須が組み合わさり、初回途中失敗を再開できなかった。[backup.sh](../../../infra/operations/backup.sh) は予定envや旧API containerのimageを参照していた。
- 確認済みの事実: 制御フローの確認で上記条件を確認。修正後は実shellと外部コマンドダブルによる失敗/再開回帰で検証する。
- 未確認事項: AWS実S3失敗・実ホスト再起動を伴う復旧。本回帰はプロセス途中失敗を扱い、ディスク喪失の復旧とは区別する。

## 原因と対応

- 原因: 正常経路とDBの復元だけを確認し、公開前backup失敗後の再実行と、予定/稼働中/DB適用済みのreleaseの差を検証していなかった。
- 修正: [release-state.sh](../../../infra/operations/release-state.sh) と配備側でpending/appliedを保存し、同じimage IDの再開だけを許可する。backupはDB適用済み記録だけを参照し、共通lockとpending拒否で移行途中の誤記録を防ぐ。
- 正本: [運用手順](../../../infra/operations/README.md) に状態の意味、再開・復旧時の記録の扱いを追加。C-I07へ配備状態の検証条件を記載。
- 再発防止: [回帰テスト](../../../infra/test/release_workflow_test.py) をJest経由で通常infra checkへ組込み。実Docker/AWSは使わず、実shellの失敗箇所を制御する。
- 適用範囲: Lightsail運用のみ。サーバーのmigration/業務仕様を変更しない。
