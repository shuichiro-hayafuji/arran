# FB-20261123-01: 同意撤回の順序とDB移行の検証

- 発生日・最終更新日: 2026-11-23
- 状態: 対応中
- 対象領域: 外部AI送信同意、PostgreSQL移行
- 関連ルール: [B-S06](../../server/business.md)、[C-S03・C-S07](../../server/conventions.md)
- 出典: 2026-11-23、Issue #132の実装候補に対する独立レビュー

## 指摘と根拠

同じ利用者の撤回が並行した場合、一つが完了した後に本人が再同意すると、別の撤回呼出しが完了を受け取る前でも新しい送信を認める実装だった。この順序を同意の契約に明記しておらず、決定論的な回帰も不足していた。また、016移行の新規DBテストだけでは実際の015からの移行、失敗時のロールバック、既存データの保持を確認できなかった。接続プールを閉じた試験を実際のネットワーク断やプロセスクラッシュと区別する必要もあった。

## 原因と対応

撤回開始と完了を分け、両方の撤回が記録された後、最初の完了・再同意・新送信・もう一方の完了観測という順序を専用DBで固定した。既存挙動の契約を[DBスキーマ](../../../server/docs/database-schema.md)へ明記した。実際の015までのSQLで作成したDBへユーザーとプレビューを保存し、016のDDL途中で重複関数エラーを注入してロールバック、再適用、既存データ維持と初期版未設定を検証する。テスト専用のプール終了と実接続断・クラッシュは区別した。既存のB-S06とC-S03/C-S07を適用し、新しい全領域共通ルールは追加しない。

## 検証と判定

- `go test -race ./internal/infrastructure/persistence/postgres -run '^TestAIConsent' -count=1 -v`: PASS。専用PostgreSQLで撤回順序・v15からの移行・プール終了を含む4テスト。
- `python3 tools/harness.py check server`、`check postgres`、`check postgres-roles`、`check docs`: PASS。PostgreSQL 16の専用DBを使用。
- 変更前に上記の順序固定・015からの移行テストは存在せず、修正前の失敗再現は未実施。
- 実際の接続断とプロセスクラッシュは未検証。実送信接続前に、外部処理終了の判定、結果不明の解消・監査と権限分離を設計・検証する。これらが済むまで対応中とする。

## 履歴

- 2026-11-23: レビューを受けて契約と回帰を追加。実接続断・クラッシュは未検証として保持。

## 後続の撤回との競合（再レビュー）

先行する二つの撤回が記録された後、一方の完了、再同意、結果不明の新送信、後続の撤回開始を経て、もう一方が完了を確認する場合を再レビューで指摘された。実装には世代番号がなく、先の要求も後続の保留を待つため、「最初の保留解除時点で全呼出しが完了」という以前の説明は不正確だった。安全側の待機を維持し、後続の保留に巻き込まれ得る制約を正本へ明記し、順序を固定した専用DB回帰を追加した。
