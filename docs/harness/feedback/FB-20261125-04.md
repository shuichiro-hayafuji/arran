# FB-20261125-04: 退会バッチの時刻境界と未完了処理

- 発生日・最終更新日: 2026-11-25
- 状態: 対応中
- 対象領域: 退会受付・日次バッチ・ReminderWorker
- 関連ルール: [B-S06](../../server/business.md)、[C-S07](../../server/conventions.md)
- 出典: Astra 6.2 medium 独立レビュー

## 指摘と対応

0時直前に開始した受付がユーザー行ロック待ちとなり、0時バッチの一覧取得後にコミットすると、その日のバッチから漏れる。トランザクション開始時刻を申込時刻とするだけでは解決しない。受付の共有 advisory ロックとバッチの排他ロックで、コミットまでを時刻境界と直列化し、申込時刻にはロック取得後の `clock_timestamp()` を使う。

一人のユーザーロックが長時間保持されても、他の利用者を一括で待たせ続けないよう各ロックに timeout を設定する。失敗は未完了のまま残して service を失敗させ、再試行する。開始済みの ReminderWorker は期限所有者列挙とチャット保存時の両方で本人の活動状態と退会申込を確認する。

追加レビューでは `docker compose exec` の timeout だけではコンテナ内プロセスの終了を保証できず、DB処理が残り得ると指摘された。バッチのアプリ境界でDB接続から終了まで4分の context deadline を設け、systemdの5分 timeout と別に制限する。実DBでは短い期限を用い、ロック待ち中の期限切れで対象を未完了に保ち、ロック解放後の再試行で完了することを確認する。

## 検証と残り

隔離 PostgreSQL で受付コミット遅延・時刻境界、ReminderWorker の選定と受付後の書込み拒否、利用者ごとのロック待ちと再試行を確認する。全認証済み HTTP 処理の drain と、古いバックアップに退会状態が戻る問題は未完成であり、受付は引き続き強制停止中。
