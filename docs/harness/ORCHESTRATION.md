# Codexオーケストレーション

## 目的

Codex Appのmain sessionとサブエージェントの責務、Issueからモデルを選ぶ規則、実装・レビュー・検証の順序を定める。複数のエージェントを使っても、作業範囲、既存差分、検証結果、未確認事項を一つの責任主体で管理する。

## main sessionの責務

main sessionは成果物の統括者であり、次を担当する。

- ユーザーの依頼、対象Issue、完了条件、対象外を確定する。
- 変更前に守る対象と検証方法を定める。
- Issueの`AI実行クラス`を確認し、本書の表に従ってサブエージェントのモデルと推論強度を指定する。
- 調査、実装、レビュー、検証の順序と各エージェントの作業範囲を決める。
- 同じ作業ツリーでソースへ書き込むエージェントを同時に一つだけにする。
- explorerの証拠から実装方針を決め、reviewerの指摘を採用・保留・却下し、verifierの結果から完了可否を判断する。
- ユーザーへの質問、権限確認、進捗、変更内容、検証結果、未検証範囲を報告する。
- commit、push、PR、Issue、GitHub Projectsなど外部状態の変更を、ユーザーの依頼範囲と対応するSkillに従って統括する。

通常の機能実装はarran_implementerへ委譲する。main sessionが小さな統合作業やオーケストレーション設定を直接編集する場合も、implementerと同じ対象ルールと検証手順に従う。

## サブエージェント共通の境界

- main sessionから指定された対象、完了条件、読み書き範囲だけを扱う。
- 作業範囲、アーキテクチャ、Issueの状態、モデル選択を独自に変更しない。
- 判断材料や権限が不足する場合は推測で進めず、事実と必要な判断をmain sessionへ返す。
- ユーザーへの質問、別エージェントへの再委譲、commit、push、PR作成、Issue・Project更新を行わない。
- 自分の結果を最終的な承認や完了判定として扱わない。
- 指定範囲外の既存差分を変更、退避、破棄しない。

## 役割

| 役割 | 担当 | 担当しないこと |
| --- | --- | --- |
| main session | 範囲・モデル・順序の決定、判断、統合、外部反映、最終報告 | 通常の機能実装を無条件に抱え込むこと |
| arran_explorer | Issue、ルール、コード、テスト、履歴の調査と証拠整理 | 編集、方針決定、完了判定 |
| arran_implementer | 確定範囲の実装と必要な回帰テスト | 範囲拡大、外部反映、完了判定 |
| arran_reviewer | 完成候補の差分に対する独立レビュー | 編集、最終承認、Issue更新 |
| arran_verifier | 正規コマンドの実行と結果分類 | 実装修正、期待値変更、成功への読み替え |

implementerは変更を保証するテストを作成して実行する。verifierは実装とテストを変更せず、独立して正規の検証を再実行する。専任のtest-authorは、独立した大規模な結合テストやE2E設計が必要になったときに追加を検討する。

## IssueのAI実行クラス

GitHub Projectの単一選択フィールド`AI実行クラス`に、`標準`または`重点`のどちらか一つを設定する。製品上の優先度であるP1・P2・P3から自動変換しない。

次の条件に一つでも該当するIssueは`重点`、該当しないIssueは`標準`とする。

- 認証、認可、ユーザー所有権、アカウント復旧を変更または検証する。
- 個人情報、秘密情報、LLMへ送信するデータ、同意・削除・exportを扱う。
- 金額判定、残高、支出計上、CSV重複、返金、予算履歴へ影響する。
- PostgreSQLの制約、migration、トランザクション、同時実行、障害時整合性へ影響する。
- MobileとServerのAPI契約を同時に変更する。
- HTTPS、AWS、バックアップ、復旧、署名、一般公開・停止条件を扱う。
- mobile、server、database、infraのうち三領域以上を横断する。
- 完了条件に実DB、実機、staging、AWS、障害注入、負荷検証のうち二種類以上を含む。
- 原因が未特定で、複数レイヤーを横断してデータ消失、誤助言、他ユーザー情報の表示につながり得る。

実装対象のIssueで値が未設定、複数相当、または現行本文と矛盾する場合、main sessionは実装前に上記条件で再判定し、根拠とともにProjectへ反映する。Projectへ反映できない場合は、判定と未反映理由を報告してから作業範囲を決める。

## モデル選択

| 対象 | `標準` | `重点` |
| --- | --- | --- |
| main session | `gpt-5.6-sol` / `medium`を既定とし、Appでタスクごとに変更可能 | 必要な場合だけAppでAstraへ変更する |
| arran_explorer | `gpt-5.6-luna` / `medium` | `gpt-5.6-sol` / `medium` |
| arran_implementer | main sessionのモデルと推論強度を継承 | main sessionのモデルと推論強度を継承 |
| arran_reviewer | `gpt-5.6-sol` / `high` | `gpt-6-astra` / `medium` |
| arran_verifier | `gpt-5.6-luna` / `medium` | `gpt-5.6-luna` / `medium` |

explorerとreviewerのTOMLにはモデルを固定せず、main sessionがspawn時に明示する。重点のreviewerでAstraを利用できない場合はSol / highへフォールバックし、変更理由を報告する。

利用枠を守るため、SolまたはAstraのサブエージェントを同時に複数動かさない。Astra reviewerは実装途中の差分ごとに起動せず、レビュー可能な完成候補に対して使用する。Fast modeは定常設定にせず、利用する場合はmain sessionが必要性を判断する。

## 実行順序

1. main sessionが依頼、Issue、完了条件、AI実行クラス、守る対象、検証方法を確定する。
2. 必要な場合、explorerが証拠と影響範囲を調査する。
3. main sessionが調査結果から実装範囲と方針を決定する。
4. implementerが実装と必要な回帰テストを行い、対象範囲を検証する。
5. 完成候補に対してreviewerとverifierが独立して確認する。この二者はソースへ書き込まないため並行実行できる。
6. main sessionが指摘と検証結果を判断し、必要ならimplementerへ範囲を限定して差し戻す。
7. 修正後に必要なレビューと検証を再実行し、main sessionが差分、結果、未検証範囲を確認して報告する。

小さく明確な変更で調査が不要な場合はexplorerを省略できる。文書だけの変更にアプリ全体のビルドを一律に要求しない。どの役割を省略しても、main sessionの最終確認と実際の検証結果の報告は省略しない。
