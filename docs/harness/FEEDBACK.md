# 実装への指摘からの自己改善ループ

このループの「学習」は、このリポジトリの正本ルール・テスト・改善記録を更新し、次回の作業で参照することを指す。モデルの再学習やCodexの個人メモリ更新ではない。通常の修正と同じ作業内で進め、別途の定期実行は前提にしない。

## 発火条件と記録

- ユーザーやレビューから実装への指摘を受けたとき、回帰不具合を確認したとき、既存ルールの不足・曖昧さ・見落としを発見したときに実施する。
- [改善記録の一覧](feedback/INDEX.md) を検索し、同じ原因・適用範囲の記録があれば追記する。新規の場合は [テンプレート](feedback/TEMPLATE.md) をコピーし、`FB-YYYYMMDD-NN.md` を作る。IDは既存と重複させず、一覧も同時に更新する。
- 指摘の要約、出典（レビューURL、または会話の日付と要旨）、対象コード、期待結果と実際の結果を記録する。機密情報・トークン・生のユーザーデータや会話全文は転記しない。
- 指摘はまず仮説として扱う。コード・既存契約・再現結果に照らして、確認済みの事実と未確認事項を区別する。好みの提案や単発の誤りを無条件に全領域の規則へ拡張しない。

## 修正と再発防止

1. 対象の実行経路と関連ルールIDを確認し、原因を特定する。既存ルール違反、ルール不足、検証不足など、なぜ通常の作業で防げなかったかを記録する。
2. 許可された範囲の実装を修正する。指摘が誤認なら根拠を示して不採用にし、要件の判断が必要ならその論点だけを保留にする。独立して進められる修正は継続する。
3. 再利用できる知見は [正本の配置](WORKFLOW.md#正本) に従って既存ルールへ反映し、既存IDを維持する。既存ルールで十分なら本文を重複追加せず、参照経路や検証の不足を直す。改善記録は根拠とリンクを残す履歴であり、新たなルール本文の置き場にはしない。
4. 振る舞いの不具合は可能な限り回帰テストで固定する。機械判定できる反復的な違反はchecker化を検討する。追加checkerには違反を検出するテストと許可された例外を通すテストを付ける。文章表現だけの修正等でテスト不要なら理由を記録する。
5. [tool Index](../../tools/INDEX.md) の該当scopeを実行し、コマンド、結果、未検証範囲を記録する。回帰テストは可能なら修正前の失敗と修正後の成功を確認する。確認できなかった場合はその限界を明示する。
6. 差分レビューで実装・正本・検証の対応を確認し、記録と一覧の状態を更新してユーザーへ報告する。指摘への対応を口頭の約束だけで終えない。

指摘を解消するためにテストを弱めたり、既存違反を一律に例外化したりしない。責務変更が必要なら理由・影響・関連ルール・検証を同じ変更に含める。無関係な一括修正は行わない。

## 状態と完了条件

| 状態 | 意味・遷移条件 |
| --- | --- |
| 未確認 | 指摘を記録した段階。根拠を調べ、対応中・保留・不採用へ進める |
| 対応中 | 原因を確認し、実装・再発防止・検証を進めている |
| 保留 | 判断や実行環境が不足。理由、次の具体的な行動、再開条件を必須とする |
| 完了 | 修正または修正不要の根拠、正本への反映または不要理由、再発防止策、必要な検証結果が揃っている |
| 不採用 | 指摘を適用しない根拠を確認済み。理由を残す |

必要な検証がFAIL・BLOCKED・未実行なら完了にしない。静的検証で実機・DB・AWS検証を代用しない。次の作業では一覧の対象領域の未完了項目を読み、適用済みの知見は通常の正本文書から参照する。同じ問題が再発したら完了・不採用の記録も対応中へ戻し、発生日と既存対策で防げなかった理由を追記する。過去の結果を消さない。
