# 復元照合用の独立証跡: 未接続の設計案

この文書と `server/internal/restoreevidence` は設計途中の部品であり、退会受付・復元 DB の切替・再公開を許可しない。権威の確立、アプリへの接続、DB への照合・再適用、権限と実環境の検証はいずれも未実装である。

作業仮定として、PostgreSQL と DB backup とは異なる DynamoDB テーブルを証跡の権威とする。同一 AWS アカウントと同一 region に置く限り、アカウント侵害、管理者の権限変更、region 障害の独立性は保証しない。別サービスに置くだけで改ざん耐性や真正性を満たしたとは扱わない。

- 権威にはランダムで不変な ledger ID、連続した世代、各世代のイベントと前世代の digest を持たせる。DB の連番 user ID や変更可能な username は本人の照合キーに使わない。本人ごとのランダムな不変 ID を新規導入し、既存データへの移行と重複防止・別人照合拒否を検証する必要がある。
- head とイベントは条件付き原子更新で同時に進め、競合、未確定応答、権限エラーは成功と扱わない。重複操作の識別子と結果照会、同意・退会・送信開始/完了それぞれの DB と外部記録間の中断・復旧手順が必要である。DB の commit と外部テーブル書込みは一体ではないため、順番と途中状態を明確にしなければならない。
- 復元時は書込み・送信と公開を停止し、復旧専用権限で正しい table と region を指定して強整合な head を取得する。その後、全イベントを取得し head と連続性を照合する。取得できない、欠損、旧世代、同一性不一致、読取結果不明、実行中の書込みが排出されない場合は非公開のままにする。単に保存済み head のハッシュが合うことは、取得 head が最新である根拠にはならない。
- 読取り後から公開完了まで head が変わらないことを別途保証し、証跡にある退会状態・セッション失効・同意の撤回・結果不明送信を復元 DB に照合・反映してから再検証する必要がある。孤立イベント、完全な空の証跡、利用者の欠落、途中失敗、部分反映、再試行の意味は今後定義する。
- アプリの追加、復旧時の読取、削除・管理の権限を分離し、実際の IAM・テーブル設定・接続先の本人性を確認する。削除や権限変更を含む管理者侵害への耐性は別途設計する。テーブル、鍵、権限、課金設定をこの変更では作成しない。

純粋な `ValidateChain` は入力された head を仮に権威とした場合の構造検査だけを行う。外部ストアからの取得、強整合性、固定期間、権限、時点の鮮度、正しい人物との対応、イベントの意味や DB への適用を保証しない。偽の古い head と整合する古いイベントは拒否できない。証跡件数に応じた read/write・保存・監視・障害対応費用も構成と負荷が未定のため未見積りである。

`CheckRestoreEvidence` は未接続の限定検査で、証跡に現れる owner ID が候補一覧に存在するか一方向に検査し、未知・重複 owner と未完送信を拒否する。候補にだけ存在する owner は許容するため、候補側の全員を証跡と照合したことにはならない。現行イベントには退会申込時刻がなく、同意の再適用に必要な基準状態・遷移も未定義のため、退会・同意イベントを含む履歴はすべて拒否する。一覧に ID があることは本人との対応を証明せず、成功しても DB の変更や公開は許可しない。信頼できる head・候補 DB の固定、本人確認と再適用は別途必要である。

退会イベントの v2 は未接続の試作として、UTC 正規形式の申込時刻と、完了からの申込 operation ID 参照をダイジェストに含める。v1 のダイジェスト形式は変更しない。DB には本人・操作 ID・版・時刻・申込参照を未確認の prepared 状態として保存・再読できるが、時刻の取得元や外部記録との一致を証明せず、受理・復元・公開の根拠にはならない。検査は v2 単独の退会履歴のみを対象とし、v1 との混在、AWS への永続化、証跡の確定は扱わない。

v2 の未確認行には、外部書込み前の世代・前世代 digest・イベント digest を固定し、同じ値のみ再試行できる。DB の commit 応答が不明な場合は、固定済みの値を読み戻して照合する。現状、lease の有効確認後から DB commit まで、lease 失効や別 writer の動作を排除できないため、v2 を witnessed にする操作は DB 制約で禁止する。固定成功は外部書込みや受理の成功を意味しない。

未接続の再開試作では、外部書込み前に正確な世代と digest を DB に固定する。固定後に別操作が head を進め、元の世代で書けなくなった場合は `ErrManualHold` とし、操作を自動的に新しい世代へ載せ直さない。外部と DB の両方の原記録を調査し、適用・送信・公開を停止する。安全な人手解決・再開手順は未実装である。

## 実装候補の現在地

未接続の候補には、DB の本人 ID・intent・試行固定・receipt、DynamoDB の条件付き head/event/operation 記録、所有者と同意版を照合する送信開始・完了、強整合 readback、停止 lease、これらをつなぐテスト用 bridge がある。DB と fake の権威を使う結合回帰は実環境の認証、ネットワーク、課金、IAM や独立障害を証明しない。lease は自動失効しないため、取得・解放が不明な場合やプロセス喪失時は自動的に再取得できず、調査と安全な復旧手順が必要である。

本番に接続するには、少なくとも以下が残る。

- 正しい AWS account、principal、region、table と table ID を使う単一の検証可能な SDK 設定を固定し、STS と DynamoDB の主体が一致しない構成や endpoint の差し替えを拒否する。現在の候補は別クライアントを注入でき、DescribeTable の検査後に同名 table が再作成される競合を防げない。
- アプリ・復旧・削除/管理の権限、table の再作成防止、直接クライアントと旧 image の迂回防止を実環境で検証する。候補 wrapper だけでは権限分離を保証しない。
- すべての該当 writer を共通の lease と条件付き transaction に通す。head 取得から再公開まで lease と公開停止が継続していることを確認し、孤立イベント、head 巻戻り、欠損、結果不明、監査ログを扱う。
- `evidenceflow` と PostgreSQL journal を実際の受付・batch・外部 AI 同意・送信経路に結び、DB と外部の各 commit の前後・応答喪失・再起動・同時処理で、外部の記録と本人が確定するまで副作用を許可しない。候補は現在どの本番経路にも接続されていない。
- 退会申込と完了、同意の版と撤回、送信の開始と終了、session 失効を復元候補 DB に安全に再適用し、旧 backup・別人・欠損・不一致・途中失敗を拒否する実装と復旧訓練が必要である。UUID 発行前の backup では本人を数値 ID から推定しない。

これらが揃うまで `withdrawalRuntimeReady=false` と復元切替の拒否を維持する。利用料金、保持期間、監視、障害時の人的対応、同一 account・region 障害の扱いは未確定である。
