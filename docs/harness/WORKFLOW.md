# 運用・検証範囲

## 変更の進め方

1. Indexから対象領域の3文書を選び、該当ルールIDとコードを確認する。
   [改善記録](feedback/INDEX.md) で対象領域・関連ルールIDの未完了項目を確認し、今回の変更に関係するものを検証計画へ含める。
2. 変更で影響するAPI・永続化・利用者の操作・他領域を確認する。
3. 実装と必要な回帰テストを更新し、toolの対象scopeを実行する。
4. 業務・依存方向・データ境界は差分レビューで確認する。toolの成功で代用しない。
5. 実行結果と未検証範囲を報告する。ルールを変えた場合はIDを維持して本文と関連検証を更新する。
6. 実装への指摘があった場合は [自己改善ループ](FEEDBACK.md) を実施し、改善記録の状態・正本への反映先・残る検証を報告する。

## 正本

- 領域固有の業務ルール・アーキテクチャ・実装作法は [領域別Docs](../README.md) の各ルール文書、このハーネスの運用・検証ルールは本ディレクトリを正本とする。HTTP契約は [OpenAPI](../../server/docs/openapi.yaml)、実DBスキーマは [PostgreSQL migration](../../server/internal/infrastructure/persistence/postgres/002_auth.sql) を含むバージョン付きSQLを正本とする。
- [領域別アーキテクチャ資料](../README.md) とREADMEは説明資料。コードとの差異を発見した場合、過去の記述だけを根拠にコードを作り替えない。意図を確認し、必要な文書を同じ変更で整合させる。
- 業務ルールは利用者に約束する結果を記述する。配置・依存はアーキテクチャ、エラー処理や変更の進め方は実装作法、機械的なコマンドはtoolへ置く。
- 同じルールの本文を複数ファイルにコピーせず、IDとリンクで参照する。

## この初版で保証する範囲

- 文書の分割と参照経路、既存formatter・analyzer・testへの共通CLIを提供する。
- モバイルの共通HTTP生成境界（A-M07）はtoolで字句検査する。依存方向全体、API互換性、送信データ最小化は差分レビューと既存テストで確認する。
- PostgreSQL統合テストは専用scopeで実行する。通常のserver scopeではDBを使わない。実機E2EとAWS配備はこのCLIに含めない。
- 新規checkerを追加する際は「違反を入れると失敗する」「既存例外を誤検出しない」をテストする。
- serverの依存チェッカーはproductionのGo import、パッケージ配置、Agent取引DTOの許可項目を検査する。金融判断の実装内容と既存項目へ詰める値の意味は差分レビューで確認する。

## 業務方針を決めるIssue・エピックの記述

### 作成前に決めること

読み手を「この調査やコードを読んでいない業務担当者」とする。監査メモは根拠として使い、短文をそのままIssue本文やタイトルへ転記しない。まず、利用者が困る場面、決めたい問い、決定を使う機能・運用、完了の証拠を言葉にする。

### 初稿の作り方

- タイトルは「何をどうするか決める」「何ができるようにする」と、作業の到達点を書く。「未確定」「不足」だけで終わらせない。
- 本文は背景と目的 → 決めること → 完了条件の順で、前の説明を知らなくても理解できるように書く。エピックは全体で何が決まるかと、各子課題の役割を説明する。
- 抽象的な判断には、日常の操作や金額を使った例を添える。例えば「予算履歴を定義する」なら「予算を3万円から4万円に変えたとき、先月の残額も変えるか」と問う。例示や選択肢を決定済みの仕様にしない。
- コードの値や専門用語を利用者の操作へ翻訳する。例えば`spent`は「使ったと記録した支出」。必要な用語は最初に意味を説明し、内部IDやコード参照は根拠として末尾へ置く。
- 完了条件には何を決め、どの場面で何を確認するかを書く。「設計・検証する」だけで済ませない。実測・実装・実機確認が元の範囲に含まれる場合、方針を書くだけで完了へ変えない。
- 関係のない注意書きを全Issueへ一律に追加しない。読みやすさのために必要な前提を削ったり、短さだけを目的に名詞・略語を連結したりしない。

### 提出・投稿前の確認

初稿の作成と、意味を確認するレビューを別工程にする。複数件を作る場合も、代表例のレビューを全件の検査の代わりにしない。ユーザーへ確認を求める前に、全件について次を確認し、自分で直す。

1. 本文だけを読んで「誰がどんな場面で困り、何を決めるのか」を具体的に言い直せるか。元のメモやコードを見ないと答えられなければ説明を補う。
2. 決定後にどの機能・表示・運用が変わるか、何を証拠に完了とするか分かるか。
3. 原文と照合し、判断事項・対象外・必要な実装や検証を落としていないか。例を仕様に変えたり、未決定事項を勝手に決めたりしていないか。
4. 更新の場合は現行本文・ラベル・親子関係と照合したか。優先度は現行ラベルを正とし、文章修正で状態や関係を変更しない。

日本語の推敲をサブエージェントへ依頼する場合は、読み手・具体的な問い・守るべき元の範囲を渡す。主エージェントは元の範囲との一致を確認し、推敲を任せたことだけを品質保証としない。サブエージェントを使わない場合も、同じレビューを行う。投稿後は実際の本文を再取得して確認する。件数・リンク・構文の検査成功は、日本語の意味やリモート反映の証明ではない。
